# Архитектура Zales

Документ описывает границы модулей, потоки данных и жизненный цикл туннеля.
Обоснования отдельных выборов вынесены в [ADR](adr/).

---

## 1. Принципы

1. **Движок за интерфейсом.** Слой приложения не знает, что внутри Xray. Он работает с
   `TunnelEngine`. Добавить второй движок — значит добавить модуль, а не переписать приложение.
2. **Туннель в отдельном процессе.** Нативный код (Go-рантайм Xray, C-код tun2socks)
   живёт в процессе `:tunnel`. Падение или утечка в нативном коде не роняет интерфейс,
   а память процесса возвращается системе при остановке.
3. **Однонаправленный поток данных.** Состояние течёт вверх через `StateFlow`, события —
   вниз через явные команды. Никаких двусторонних связей между слоями.
4. **Один Go-рантайм на процесс.** Ограничение gomobile. Все Go-зависимости собираются
   одним вызовом в один AAR. См. [ADR-0003](adr/0003-single-go-runtime.md).
5. **Ключ не покидает своего слоя.** `:core:storage` отдаёт наверх дескриптор ключа, а
   не сам секрет. Секрет разворачивается только в момент сборки конфигурации, в процессе `:tunnel`.

## 2. Карта модулей

```
zales/
├── build-logic/              convention-плагины Gradle: android-library, compose, kotlin-jvm
│
├── app/                      хост Compose, навигация, граф зависимостей, точка входа
│
├── core/
│   ├── common/               Result, диспетчеры, логирование, время, отпечаток сети
│   ├── design/               ДИЗАЙН-СИСТЕМА: токены, шейдеры, компоненты, движение
│   ├── storage/              шифрованное хранилище ключей, настройки, профили сетей
│   └── voice/                «Приговорки»: корпус, движок подбора, правила безопасности
│
├── parsing/                  ссылки любых форматов → AccessKey
│
├── tunnel/
│   ├── api/                  TunnelEngine, TunnelState, TunnelCommand, TunnelFailure
│   ├── engine-xray/          мост к libXray + сборщик конфигурации Xray
│   ├── autopilot/            лестница стратегий, гонка, профили сетей, сторож
│   ├── diagnostics/          движок проб и таксономия отказов
│   └── service/              ZalesVpnService, AIDL, плитка, приёмник загрузки
│
├── feature/
│   ├── onboarding/           первый запуск и вклейка ключа
│   ├── home/                 главный экран: чаща и рубильник
│   ├── key/                  управление ключом, QR, «ключ по наследству»
│   ├── diagnostics/          экран «Проверка тропы»
│   └── settings/             настройки, включая «Только рубильник»
│
└── native/                   сборочные скрипты (Python/shell), не модуль Gradle
    └── core/                 → zales-core.aar
```

**Правило зависимостей.** `feature/*` зависит от `core/*` и `tunnel:api`, но **никогда**
от `tunnel:engine-xray`. Реализации подставляются в `app` через граф
зависимостей. Это проверяется тестом на граф модулей в CI.

## 3. Процессы

| Процесс | Что живёт | Почему |
| --- | --- | --- |
| основной | Compose UI, навигация, хранилище настроек | Быстрый холодный старт, никакого нативного кода |
| `:tunnel` | `ZalesVpnService`, libXray, автопилот, сторож | Изоляция падений, возврат памяти при остановке, переживает смерть интерфейса |

Общение — через **AIDL**: `ITunnelService` (команды) и `ITunnelCallback` (поток состояния).
В основном процессе поверх AIDL лежит `TunnelController`, который отдаёт наружу обычный
`StateFlow<TunnelState>` — интерфейс о существовании AIDL не знает.

## 4. Поток данных

```
  ┌─────────────── основной процесс ────────────────┐   ┌──────── процесс :tunnel ────────┐
  │                                                 │   │                                 │
  │  Compose UI                                     │   │   ZalesVpnService               │
  │      ↑ StateFlow<UiState>                       │   │        │                        │
  │  ViewModel                                      │   │        ├── Autopilot            │
  │      ↑ StateFlow<TunnelState>   команды ↓       │   │        │     ├── StrategyLadder │
  │  TunnelController ──────── AIDL ────────────────┼───┼───────▶│     ├── Racer          │
  │      ↑                                          │   │        │     ├── NetworkProfile │
  │  KeyRepository ── дескриптор ключа ─────────────┼───┼───────▶│     └── Watchdog       │
  │      ↑                                          │   │        │                        │
  │  EncryptedStore (Android Keystore)              │   │        └── XrayEngine → libXray │
  │                                                 │   │              (inbound «tun»)     │
  └─────────────────────────────────────────────────┘   └─────────────────────────────────┘
```

**Внутри процесса `:tunnel`** цепочка выглядит так:

```
VpnService.Builder → tun fd ──▶ xray.tun.fd ──▶ Xray: inbound «tun» на gVisor ──▶ застава
                                 (из Go)                    (Go)
```

Между дескриптором и ядром **нет ничего** — ни tun2socks, ни локального порта
([ADR-0007](adr/0007-native-tun-inbound.md)). Открытый SOCKS на `127.0.0.1` мог бы
просканировать любое приложение на телефоне и опознать по нему VPN-клиент; здесь
сканировать нечего.

## 5. Жизненный цикл туннеля

```
             ┌──────────┐
             │   Idle   │◀────────────────────────────┐
             └────┬─────┘                             │
      команда     │                                   │ остановка
      «открыть»   ▼                                   │
          ┌───────────────┐  разрешение не выдано  ┌──┴────────┐
          │  Preparing    ├───────────────────────▶│  Failed   │
          │ (разрешение)  │                        └──┬────────┘
          └───────┬───────┘                           │
                  ▼                                   │ все стратегии
          ┌───────────────┐                           │ исчерпаны
          │   Probing     │───────────────────────────┘
          │ гонка стратегий│
          └───────┬───────┘
                  │ первая победившая
                  ▼
          ┌───────────────┐   сторож увидел деградацию   ┌──────────────┐
          │  Connected    │─────────────────────────────▶│   Degraded   │
          │               │◀─────────────────────────────┤              │
          └───────┬───────┘        восстановилось        └──────┬───────┘
                  │                                             │ не чинится
                  │ сеть сменилась                              ▼
                  │                                     ┌──────────────┐
                  └────────────────────────────────────▶│ Reconnecting │
                                                        └──────────────┘
```

Состояния — это `sealed interface TunnelState`. Каждое несёт ровно те данные, которые
имеют смысл именно в нём: `Probing` знает, какая стратегия проверяется сейчас и какая по
счёту; `Connected` — время подключения, задержку, объём трафика и имя победившей
стратегии; `Failed` — запись из таксономии отказов, а не строку с текстом ошибки.

Отдельно: **`Degraded` — не ошибка.** Пользователю это показывается как «тропа сузилась,
ищу обход», интерфейс не мигает красным, рубильник остаётся включённым.

## 6. Сборка конфигурации Xray

`XrayConfigBuilder` собирает JSON из трёх независимых источников:

1. **`AccessKey`** — что за застава: адрес, протокол, учётные данные, транспорт.
2. **`Strategy`** — как именно к ней идти сегодня: фрагментация, отпечаток uTLS, режим
   XHTTP, порт, обход по IP. См. [CONNECTIVITY.md](CONNECTIVITY.md).
3. **`RoutingPolicy`** — что заворачивать в туннель: раздельная маршрутизация,
   исключённые приложения, правила для локальных сетей.

Именно разделение ключа и стратегии делает возможным автопилот: один ключ порождает
десяток конфигураций, среди которых идёт гонка.

Сборка конфигурации — **чистая функция**, покрытая тестами на снимках: `(AccessKey,
Strategy, RoutingPolicy) → JSON`. Это позволяет проверять генерацию всех комбинаций без
запуска ядра.

## 7. Нативные артефакты

Ни один нативный бинарник не лежит в репозитории. Их собирает CI и публикует в релиз с
тегом, привязанным к версии ядра. Gradle тянет их оттуда с проверкой контрольной суммы.

| Артефакт | Из чего | Чем собирается | Куда |
| --- | --- | --- | --- |
| `zales-core.aar` | libXray (MIT) + Xray-core (MPL-2.0) | gomobile, Go 1.24+ | GitHub Release `core-v26.9.9` |

ABI: `arm64-v8a` и `armeabi-v7a`. `x86_64` — только для отладочных сборок под эмулятор.

## 8. Технологический стек

| Слой | Выбор |
| --- | --- |
| Язык | Kotlin 2.3, строгий режим, explicit API для библиотечных модулей |
| Интерфейс | Jetpack Compose, Material 3 как основа токенов, но собственная визуальная система |
| Графика | AGSL `RuntimeShader` (API 33+), запасной путь на `Canvas` для API 26–32 |
| Асинхронность | Coroutines + Flow, структурированная конкурентность |
| Зависимости | Hilt |
| Хранилище | DataStore Proto + `EncryptedSharedPreferences` поверх Android Keystore |
| Сборка | Gradle 9 с version catalog и convention-плагинами |
| Тесты | JUnit5, Turbine (Flow), Kotest property-based, Robolectric, Macrobenchmark |
| Минимальная версия | Android 8.0 (API 26); целевая — актуальная на момент релиза |

---

## 9. Что сознательно не делается

- **Нет своего сервера и нет своего протокола.** Zales — клиент к вашей заставе.
- **Нет аккаунтов, аналитики и удалённой конфигурации.** Приложение не имеет ни одного
  сетевого адреса, кроме вашего ключа и проверки обновлений на GitHub, которую можно выключить.
- **Нет встроенного списка бесплатных серверов.** Это чужая ответственность и чужой риск.
- **Нет второго движка в первой версии.** Решение зафиксировано в [ADR-0001](adr/0001-xray-core-only.md).
